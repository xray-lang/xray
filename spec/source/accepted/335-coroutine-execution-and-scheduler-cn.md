## 3. 语言与推导模型

### 3.1 协作式调度与取消（C1）

- 只在挂起点切换：`await`、Channel、`select`、`Task.yieldNow()`、sleep、I/O 与同步原语的等待。原生代码不插入回边安全点。
- **回边不检查取消。** 理由：
  - 成本：Xray 生成 C，回边上的检查对 clang、GCC、MSVC 的优化器都可见，会以无法预测的方式扰动它们。2026-11-10 实测（§8.10）：每次迭代都检查，可向量化的循环慢 2.2–3.4 倍；每 1024 次检查一次，clang 上基本免费，GCC 上矩阵乘慢 42%、数组求和慢 14%。HotSpot 每 1000 次检查一次，是在自己的优化器里插入，能安排它不打乱循环优化；Xray 做不到。
  - 语义：任意循环都会变成取消点，可能在两次相关的写之间打断不变量。这是 Java `Thread.stop` 与 Haskell 异步异常的老问题。
  - 先例：Swift、Kotlin、tokio 都要求显式检查；Go 为抢占改用信号，没有采用回边检查。
- **显式检查**：长循环调用 `Task.checkCancelled()`。所在任务已被请求取消时，从此处进入取消展开（与 `await` 已取消任务相同，不可捕获，执行 `defer`），否则立即返回；它是取消检查点，不是让出点，在不挂起的函数中也可以调用（Swift 的 `Task.checkCancellation()`、Kotlin 的 `ensureActive()`）。在 `defer` 体内取消被屏蔽，调用立即返回（§6.17）；在 C 回调中的处理，按 Task336 的展开边界规则在实施时确定。仍可用 `Task.isCancelled()` 自行收尾，或用 `Task.yieldNow()` 让出。
- **诊断**：任务被请求取消后超过阈值仍在运行时，sysmon 报出它所在的循环（§6.4 第 4 条），用户由此知道该在哪里加检查。
- VM 不按回边计数让出，与原生保持一致；A6 的燃料计数只存在于沙箱构建。
- 用户知情的后果：`while (!flag.load()) {}` 这类自旋等待，在 SINGLE 下会永远等下去；MULTI 下置位方由其它 worker 窃取，或在全部 worker 都被占住时由长计算补位的备用 worker 运行（§6.4 第 2 条），通常能结束，但规范不保证。规范 §10.1 已写明"不含挂起点的长循环不让出"。

### 3.2 动态派发的挂起推导（C2）

1. **静态直接调用**用被调函数自身的推导结果。
2. **经接口值的调用 `s.m()`**：候选集是封闭程序中实际被转换为该接口值（或其子接口值）的全部具体类型对 `m` 的见证（RTA：只计真正发生过向上转换的类型）。任一候选可能挂起，该调用就可能挂起。
3. **经 class 接收者的调用 `a.m()`**：候选集是静态类型及其子类中被实例化的类型对 `m` 的最终实现（CHA 加 RTA）。
4. **源码上的承诺**：接口要求、class 方法或顶层函数声明为 `nosuspend fn m()` 时：
   - 每个见证或覆写都必须在自己的定义处证明不挂起，否则在该实现处报错；
   - 经该要求的调用恒不挂起，不再依赖候选集。

   这就是接口作者锁定"永不挂起"的手段。2026-11-10 用户裁决把承诺写在源码声明上，取代 Task313/314 已决边界第 1 条的 `xray.toml` `[declarations]` 载体（[声明载体](../../../../xray-docs/design/xir/xir-declaration-carrier.md)）；理由与 Task341 D2 把 extern 契约移到签名上相同：一个事实只有一个生产者，读接口的人在声明处就能看到。`nosuspend` 与函数类型前缀 `nosuspend fn(...)`（§2.8）同词，`main fn`、`sendable fn` 是同一位置的修饰（Task341 D7），多个修饰的顺序实施时确定。参数义务不需要新写法，直接写参数类型 `nosuspend fn(T) -> R`。删除 `[declarations]` 区与其解析，不留兼容；内部的承诺位（[声明效应合同](../../../../xray-docs/design/xir/xir-declared-effects.md)）不变，只换来源。
5. **候选集不闭合**（动态库导出的接口、可替换入口、extern 实现、热更新）时一律保守为可能挂起。
6. 推导只影响两件事：代码生成，以及 `nosuspend` 上下文（`nosuspend fn` 函数字面量、`CFn` 回调、deinit、ISR 与生成器函数里的 `defer` 体）的合法性。普通函数的 `defer` 体自 2026-11-12 起不在其内（§6.17）。普通调用的合法性不依赖它（Task316 §0 第 1 条）。
7. **原因链。** 诊断与 LSP 写明原因，例如"`Logger.log` 可能挂起：候选 `RemoteLogger.log`（remote_log.xr:20）→ `http.post` → `NetConn.write`"。新增一个会挂起的实现，导致远处某个 `nosuspend` 上下文报错时，诊断必须指向这个新实现。
8. 候选集与 F03 覆写派发、ROOT/NoSuspend 承诺、特化可达性是同一份事实（Task327 F03 第 5 条），不另建判据。
9. **跨包不靠推导放行**（2026-11-10，§8.11）：推导与代码生成照旧用全程序候选集；但 `nosuspend` 上下文的合法性不跨包放行。其中的派发调用，若实现可能来自声明所在包以外（公开接口的要求、可被其它包覆写的公开 class 方法），相应的要求或方法必须按第 4 条写成 `nosuspend fn`，否则在声明所在包编译时报错，提示加上 `nosuspend` 或不在此处调用。同一个包内由同一作者负责，继续靠推导放行。这样，报错总是出现在做出承诺的人那里，不会在别人加了一个实现之后落进库代码。

**不采用"派发方法禁止挂起"。** 它的代价落在 Go 最典型的抽象上：

| 案例 | 禁止挂起时的结果 |
|---|---|
| `interface Sensor { read() -> f64 }`，其中 DS18B20 要等 750 ms 转换完成 | 只能忙等（占住整个 worker），手写 `start` / `isReady` 状态机，退回函数值，或者造两套接口——最后一种就是染色 |
| `interface Store`：`PgStore` 走网络，`MemStore` 是测试替身 | 让代码可测试的标准手法被禁 |
| class 默认可继承。`stdlib/sync` 中 `Mutex`、`Semaphore` 等 9 个导出类都不是 `final`，而 `lock()` 必须能等待 | 要么全部加 `final`；要么把规则收窄到"实际被覆写的方法"，而这又需要全程序候选集 |
| 先例 | Rust 到 1.75 才允许 trait 中的 `async fn`，当时仍不支持 `dyn` 调用，社区长期用 async-trait 给每次调用装箱；Swift/Kotlin 要求协议方法标 `async`/`suspend`，等于染色 |

"禁止挂起"能带来三点好处：错误就地报告、接口调用恒为普通调用、不依赖全程序闭合。这三点由第 4 条的声明承诺按接口可选地获得。今天的使用面：demos 有 1 个接口、stdlib 有 1 个接口（`Stringable`）、共 1 处 override，都不挂起，所以两种方案对现有代码的影响都是零。

### 3.3 函数值

- 书写出的函数类型默认可能挂起（规范 §2.8），`nosuspend fn` 类型给出承诺；已构造的普通函数值不按函数体隐式强化。
- §5 O2 的效应特化只用于代码生成，不改变这条类型规则。


### 6.8 计时器（C10）

**现有实现。** `xtimer_wheel.c` 是 BEAM 时间轮的移植，源码注释写明 "ERLANG DESIGN"：

- 两个轮子：近轮 16384 格、每格 1 ms，覆盖约 16 秒；远轮 16384 格、每格 8.192 秒，覆盖约 37 小时；用分段计数跳过空格。
- 每个 worker 一个私有轮，只有拥有者能推进；其它 worker 取消时，把计时器压进拥有者的无锁取消栈。
- 计时器节点嵌在协程对象里，不单独分配；每次推进有成本上限；有确定性时间模式。

**问题。** 它不依赖协程独立堆，真正的隐含前提是抢占：

- BEAM 按 reduction 计数抢占，旧 xray 也是（`xworker_exec.c` 中的 "preempted on reductions"）。每个 worker 总能很快回到调度循环推进自己的轮子，"只有拥有者能推进"才成立。
- C1 不抢占。一个 worker 运行长计算时，它轮子上的计时器全部延后，即使其它 worker 空闲。例如任务 A `sleep(10)` 后挂在 worker 1 上，worker 1 接着运行 5 秒不让出的任务 B，A 要 5 秒后才醒。
- 旧 `sysmon_assist` 只唤醒处于休眠中的拥有者；§6.4 第 2 条的窃取只偷就绪任务，不偷计时器。
- 两个轮子共 32768 个指针槽，每个 worker 约 256 KB：hosted 上可以接受，SINGLE 与 MCU 不行。
- 到期回调读取线程局部的当前 worker，其它线程无法代为推进。
- 节点挂在旧协程对象的扩展结构上，需要迁到新任务的等待记录。

**决定。**

1. 采用分层时间轮（tokio 式）：设置与取消 O(1)，每层一个占用位图，找下一个到期时间只需每层一次移位加尾零计数。层数与每层宽度是构建参数，由下方测量决定，候选为每层 64、256、1024 格。级联时保持 1 ms 精度，不采用 Linux 内核那种以长计时器精度换取不级联的轮子。
2. 计时器可被窃取：每个轮子有一把轻量锁，拥有者走无竞争快路径；空闲 worker 找活时、sysmon 发现拥有者忙碌时，都可以推进其中已过期的部分（Go 1.14 起其它 P 可以运行计时器的做法）。
3. 到期回调只做与线程无关的唤醒（唤醒令牌），不读取当前 worker。
4. 节点放进任务的等待记录（一个任务同一时刻只等一件事），不单独分配；取消走调度器接口 §4 的等待令牌代次协议。跨 worker 取消是保留取消栈还是在锁下直接摘除，由测量决定。
5. 保留确定性虚拟时间模式，供并发测试使用。
6. 精度 1 ms，与 `time.sleep(ms)` 的单位一致；亚毫秒需要改 API，另行决定。
7. hosted、SINGLE 与 freestanding 尽量共用同一套实现；freestanding 的时间源与到期中断由 provider 提供。

**理论比较**（A 为改成可窃取后的 BEAM 双轮，C 为分层轮）：

| 操作 | A | C |
|---|---|---|
| 设置、取消 | 指令数相当；槽数组约 256 KB，随机写容易缓存未命中 | 指令数相当；结构 3–24 KB，常驻 L1 |
| 计时器真正到期 | 16 秒以内不搬动，更长的搬动一次 | 每层级联一次：每层 64 格时，64 ms–4 s 搬 1 次，4 s–4.4 min 搬 2 次；每层 256 格时，256 ms 以内不搬，65 s 以内搬 1 次 |
| 找下一个到期时间 | 有缓存；最早的计时器被取消后重新扫描，最坏 64 个计数加 512 个槽 | 每层一次位图运算，最多 6 层 |
| 每个 worker 的内存 | 约 256 KB | 每层 64 格（6 层）约 3 KB，256 格（4 层）约 8 KB，1024 格（3 层）约 24 KB |

服务器上的计时器大多是到期前就被取消的超时，此时两者相当或 C 略优；sleep 密集且计时器大多到期时，A 少 1–2 次级联。差距都在几纳秒量级，而一次唤醒加恢复要几十纳秒，所以首先按内存与"所有目标一套实现"取舍。

**测量**（S0 期间做原型）：

- 对比对象：A，以及每层 64、256、1024 格的分层轮；
- 负载：100 万次设置加取消；10 万个 1–1000 ms 的随机 sleep 并全部到期；一个 worker 被长计算占住时，其它任务计时器的到期延迟 p99；找下一个到期时间的耗时；每个 worker 的内存；
- 对照：本机 Go 的计时器设置加停止为 75 ns。

**选择规则**：分层轮在各项吞吐与延迟上与 A 相差不超过 10% 时，所有目标统一用分层轮；否则 hosted 用 A，SINGLE 与 freestanding 用分层轮。无论选哪种，第 2–5 条都必须做到。

### 6.9 主执行器（C11）

[Task341](../../../../xray-docs/tasks/341-native-ui-interop-cn.md) 规定：只能在主线程调用的原生函数是根执行流效应的一类来源；入口计划可达这类来源时，根任务整个生命周期钉在进程主线程上，`go(main)` 启动的任务和会挂起的主线程回调也只在主线程上运行。根任务和这些任务仍然是协程，可以挂起和恢复，只是每次都在主线程上恢复。本节给出调度器一侧的结构。`main` 是 `pinned`（§6.13）的特例，即钉在进程主线程上；被钉住的任务复用本节的执行器结构。

| 组件 | 设计 | 先例 | 复用 |
|---|---|---|---|
| 启用 | 入口计划可达 `main` 契约的原生来源时启用，与 NONE / SINGLE / MULTI 的选择是同一机制；不可达时不编入 | — | — |
| 任务标记 | 任务状态字增加 MAIN 位，创建时写入；唤醒时对状态字的那次 CAS 已经读到它，不多读内存 | tokio task state | §6.1 任务状态 |
| 主执行器 | 主线程拥有与 worker 相同的本地队列和 LIFO 槽，另有一个多生产者注入队列。它不在窃取名单里：worker 不偷它的任务，它也不偷 worker 的任务 | tokio `LocalSet`、Kotlin `Dispatchers.Main` | `xworker_runq.c`、`xmpsc_queue.c` |
| 唤醒路由 | MAIN 任务被主线程唤醒时进主线程的 LIFO 槽；被其他线程唤醒时进主线程的注入队列。只有主线程空闲时才投递唤醒，用一个原子标志合并，两次排空之间最多投递一次 | glib `MainContext`、winit `EventLoopProxy` | — |
| 等待方式 | 未进入宿主循环时，主执行器在平台等待原语上休眠。宿主循环由界面库掌控时（例如 `wx.run()` 一直在 C 里循环），经 Task341 §5.2 的宿主循环适配器 post / drain 运行；每次排空有时间预算（初值 2 ms），用完先交还宿主循环，再投递一次自己 | Swift `MainActor`（主调度队列） | — |
| 自旋 | 主执行器休眠或交还宿主循环之前短暂自旋（初值 20 µs，由基准调整），降低严格一问一答时的唤醒成本 | Go 的 spinning M | — |
| 计时器与 I/O | 仍由 worker 的时间轮与 netpoll 处理，到期或就绪后按唤醒路由投递到主执行器 | — | §6.8、`xnetpoll.c` |
| 阻塞与 sysmon | 主线程停在宿主循环里是正常状态，不做补位。主执行器上的单个任务连续运行超过阈值（初值 50 ms）时，报告"界面卡顿"及源码位置。全部 worker 空闲、主执行器也空闲时，sysmon 停止轮询，由下一次唤醒重新启动（Go 的 sysmon 在全部 P 空闲时同样休眠）；否则 Task341 B5 的"空闲时 CPU 为 0"做不到 | Android StrictMode | `xworker_sysmon.c` |
| 模式组合 | 主线程叠加在 NONE、SINGLE、MULTI 之上：只用界面、不用 `go` 的程序只有主线程一个线程；SINGLE 是主线程加一个 worker；MULTI 是主线程加 N 个 worker | — | — |
| freestanding | 不提供；Task341 在 Checked 阶段拒绝 `main` 契约来源 | — | — |

不采用 Go `runtime.LockOSThread` 的做法（协程绑一个专门线程、每次运行都跨线程交接），原因与实测见 §8.7。

### 6.10 后台任务与程序退出（C12）

规范 §10.12 规定：根任务的正文结束后，程序先把所有已启动的任务运行到终态，再报告完成。这保证发出去就不管的写入不会丢，但 `go ticker()` 这类后台循环会让程序永远不退出。

- `go(background) f()` 启动后台任务（§8.12），与 `go(main)` 并列：
  - 根任务与全部非后台任务到达终态后，运行时向仍在运行的后台任务发出取消请求；它们在下一个挂起点或 `Task.checkCancelled()` 处展开、执行 `defer`；全部到达终态后程序结束。与 Go、tokio 不同，后台任务的清理会执行。不含检查点的后台计算循环仍会让程序等待，由下面的诊断指出。
  - 后台任务照常返回 `Task`，可以 `await`、取消，在 `scope` 中按 scope 规则处理。
  - 只剩后台任务且都在等待、没有外部事件时，不报死锁，按上一条结束。
  - 后台任务启动的子任务是否继承后台属性，以及与 `main` 的组合，实施时确定。
- 普通 `go` 的行为不变。
- 诊断：根任务已结束、程序仍未退出时，收到 SIGINT / Ctrl-C，或 debug 构建等待超过阈值（初值 3 s），列出让程序继续运行的任务（名字、启动处、当前挂起处），格式同 §6.6 的任务转储；SIGINT 打印后按原有行为结束。

### 6.11 普通调用栈（C13）

不挂起的调用在当前线程的普通 C 栈上执行（§4 第 1 条），深递归受栈大小限制（规范 §16.4）。

- **大小**：hosted 目标上，每个任务的普通调用至少有 8 MiB 栈，各平台一致，可由运行配置调大。
  - worker（含备用 worker）与主线程都适用。运行时创建的线程按此大小创建：Unix 现已是 8 MiB（`src/os/unix/thread_unix.c`）；Windows 现在传 0，取可执行文件的默认值，通常 1 MiB（`src/os/win/thread_win.c`），需改为 8 MiB，并用 `STACK_SIZE_PARAM_IS_A_RESERVATION` 只预留、不提交。
  - macOS 与 Windows 的主线程由生成的链接参数设定；Linux 主线程跟随 `ulimit -s`，不足 8 MiB 时启动时警告。
  - 只预留虚拟地址，物理页按实际使用分配。2048 条备用 worker 预留 16 GiB，8192 个预留 64 GiB 虚拟地址，在 64 位目标上可接受。
  - freestanding 的栈由目标清单给出，不适用此保证。
- **溢出**：由守护页加信号处理捕获。Unix 在 sigaltstack 上处理 SIGSEGV / SIGBUS，并判断地址落在守护页内；Windows 用向量异常处理。处理程序打印 `stack overflow` 诊断与 Xray 调用栈（折叠重复的递归帧），以非零状态退出；不展开，不可被 `catch panic` 捕获。Rust 标准库用同一机制，Go 的栈溢出同样是致命错误。
- 不在函数入口插入栈界限检查：实测极小的递归函数 fib 慢 11–26%（§8.13），可捕获的溢出 panic 不值得让所有递归函数付这个代价。
- VM 自己的帧栈溢出时报同样的诊断；递归深度不保证与原生一致。

### 6.12 没人观察的任务失败（C14）

规范 §10.2 把任务内未捕获的异常存在 Task 中、`await` 时重抛；§10.12 规定丢弃最后一个句柄不取消任务。两条合起来，句柄被丢掉的任务失败后没有去处。本节补上（§8.14）。

- **判定**：任务以 panic 结束，且最后一个句柄已释放、也不是任何 `scope` 的成员（scope 负责观察成员）；两件事中后发生的那一刻，引用计数给出确定的报告时刻。"观察"指 `await`、`awaitResult()`，或 `poll()` 返回了终态。程序结束时，仍有句柄但从未被观察的失败也报告。
- **处理**：打印 `[Unobserved Panic]`，列出任务名、启动处、panic 消息与栈，然后按根任务 panic（规范 §8.2.4）结束程序。与 Task341 D4 对界面回调任务的规定一致。服务器要容错时，在处理函数中显式写 `catch panic`。
- **业务错误**：
  - 编译期：`Task<T, E>` 的 `E` 不是 `Never` 时，`go f()` 作为语句被丢弃（不在 `scope` 中）是编译错误，提示绑定后 `await` 或放进 `scope`；`_ = go f()` 显式放弃。
  - 运行时：绑定过却从未观察、句柄被释放的业务错误，打印 `[Unobserved Error]` 警告，不结束程序。
- 取消不是失败，不报告。
- 成本：任务上一个"已观察"位；句柄计数归零时检查一次。不需要追踪对象图。

### 6.13 钉住线程的任务（C15）

OpenGL 与 CUDA 的当前上下文、Linux 网络命名空间、Windows COM 单线程套间、JNI 的 `JNIEnv`、嵌入 Python 的线程状态，都把状态存在调用者所在的线程上，需要"这段代码始终在同一条线程上，别的代码不进来"（§8.15）。

- **写法**：`pinned` 修饰 extern 与函数，与 `main`、`safe` 并列；`go(pinned) f()` 启动被钉住的任务。

  ```xray
  unsafe extern "C" {
      safe pinned fn glClear(mask: u32)
      pinned fn setns(fd: i32, nstype: i32) -> i32
  }
  var r = go(pinned) render(win, frames)   // 独占一条 OS 线程
  ```
- **推导**：沿用根执行流效应的机制（Task322、Task341 D1）。在未钉住的任务里调用 `pinned` 来源是编译错误，诊断给出原因链。线程要求三级：无 ⊂ `pinned` ⊂ `main`。根任务与 `go(main)` 任务都满足 `pinned`；`pinned` 任务不属于根执行流，仍不能访问模块可变状态，也不能调用 `main` 来源。
- **根任务**：入口计划可达 `pinned` 来源时，根任务钉在主线程上，机制同 `main`。
- **运行时**：每个被钉住的任务独占一条新 OS 线程，线程上运行一个单任务执行器，等待与唤醒路由同 §6.9；任务可以挂起，恢复时在同一条线程上。需要消息泵的库（COM 单线程套间）复用 Task341 §5.2 的宿主循环适配器。
- **线程卫生**：任务结束后线程销毁、不复用。运行时从不在被钉住的线程上创建新线程，避免命名空间等状态被继承（由 sysmon 或专门的模板线程创建）。
- **阻塞调用**：被钉住的任务做阻塞调用时线程直接阻塞，不补位，不计入 §6.2 的线程上限。
- **共享线程状态**：不提供在同一钉住线程上再开任务的写法；由持有者任务独占，其它任务经 Channel 发消息。
- **令牌句柄**：绑定库用不可 Sendable 的令牌句柄表示线程状态，例如 `gl.makeCurrent(win)` 返回 `CurrentContext`，GL 调用都要拿着它。令牌离不开创建它的任务，任务又钉在线程上，"状态已在本线程建立"由类型保证（Task341 §7.2）。
- **成本**：每个被钉住的任务一条线程（栈 8 MiB 虚拟预留，§6.11），通常只有几个；跨线程唤醒同主执行器；未钉住的代码只是把 MAIN 位的判断换成"是否钉住"。
- freestanding 没有可钉住的线程，`pinned` 来源在 Checked 阶段拒绝。

### 6.14 任务局部值（C16）

请求 ID、追踪 span、日志字段、认证主体需要穿过整条调用链和派生的子任务，而不在每个函数上加参数（§8.16）。

```xray
const traceId = TaskLocal<string>("-")

provide traceId = newId(), user = auth(conn) {
    ...                      // 块内任意深度的调用、块内启动的整棵任务树都能读到
}

traceId.get()                // 没有绑定时返回默认值
```

- **声明**：`TaskLocal<T>` 是标准库类型，以 `const` 命名，带默认值。
- **绑定**：`provide k = v, k2 = v2 { … }` 是唯一写法。`provide` 是上下文关键字，只在语句开头、后跟"名字 ="时识别；左边必须是 `TaskLocal<T>` 的 `const`，右边类型为 `T`。块内 `return`、`break`、`continue`、`try`、`defer` 照常，块内的 `go` 照常算外层 `scope` 的成员。离开块（包括展开）时恢复。
- **读取**：`k.get()`。没有 `set`：绑定不可修改，嵌套 `provide` 只影响内层块。
- **继承**：`go`、`go(main)`、`go(pinned)`、`go(background)` 与 `scope` 成员，启动时复制当前绑定；之后父任务重新绑定不影响已启动的子任务。值须可复制且 Sendable。
- **没有当前任务的地方**（`sys.Thread` 线程体、任意线程上的 C 回调）读到默认值；同步回调发生在调用它的任务里，能看到该任务的绑定。
- **实现**：任务头一个指针指向不可变的绑定链；`provide` 压入节点、离开块时弹出；启动子任务复制指针并加一次引用计数；`get` 先取当前任务，再沿链查找。不用的程序每个任务多 8 字节。
- 按请求累计的可变状态，绑定一个可变的 Sendable 对象（内部用 `Atomic` 等），而不是修改绑定。
- `sys.ThreadLocal` 保留给 `sys.Thread` 与运行时组件：它跟着线程走，`TaskLocal` 跟着任务走。

### 6.15 worker 数与容器配额（C17）

- 默认 worker 数取以下几项中最小者，至少 2（机器或亲和掩码只有 1 个 CPU 时除外）：
  - 本进程的 CPU 亲和掩码：Linux `sched_getaffinity`，Windows 进程亲和掩码；
  - Linux cgroup CPU 上限：v2 读 `cpu.max`，v1 读 `cpu.cfs_quota_us / cfs_period_us`，向上取整；
  - Windows 作业对象的 CPU 速率上限。
- 只看上限，不看份额（cgroup `cpu.weight`、Kubernetes 的 request），否则会浪费空闲 CPU。
- sysmon 每秒重读一次。配额变化时调整：增加时启动 worker；减少时让多余的 worker 休眠，其队列被其它 worker 窃取。
- 运行配置显式指定 worker 数时不自动调整。
- 备用 worker、被钉住的线程、主线程不计入 worker 数。
- macOS 没有 cgroup，按可用逻辑 CPU 计，包括性能核与能效核。
- 不需要内存配额：Xray 用引用计数，没有 GC 堆目标。
- 规范仍不承诺 worker 数（§2）。

### 6.16 流与通道（C18）

值流与任务间通信分三层（§8.18）：

| 场景 | 用什么 | 关闭与泄漏 |
|---|---|---|
| 单生产者、单消费者、按需拉取 | 生成器（规范 §3.16） | 不需要关闭；消费者 `break` 或丢弃迭代器时生产者被关闭，已登记的 `defer` 恰好执行一次；不另开任务，背压天然存在 |
| 生产者要并发地提前运行 | `produce(容量, 迭代器)`，返回 `Receiver<T>` | 迭代器耗尽时自动关闭；消费者释放全部接收端后，内部泵任务在 `send` 处被取消，迭代器随之关闭；创建者拿不到发送端 |
| 多对多、actor 邮箱、请求应答、广播注册表 | `const (tx, rx) = Channel<T>(n)` | 引用计数驱动的自动关闭，加显式 `close()` 与 `trySend` |

```xray
fn jobs(n: i64) -> Iterator<i64> {
    for (i in 0..n) { yield i }
}
fn worker(id: i64, jobs: Receiver<i64>) {
    for (job in jobs) { print("worker-${id}: ${job}") }
}
const queue = produce(10, jobs(9))      // 同一个生成器，在调用处决定是否并发
scope {
    for (id in 1..4) { go worker(id, queue) }
}
```

- **端点**：`Channel<T>(n)` 只作为构造函数，返回 `(Sender<T>, Receiver<T>)`；不再有同时能收能发的 `Channel` 值。两端都可复制，副本共享身份，引用计数覆盖全部副本；保留多对多。签名中的 `Sender<T>` / `Receiver<T>` 表明方向。
- **自动关闭**：一端的全部副本释放，等于关闭该端。所有发送端释放或关闭且缓冲区取空时，`recv` 返回 `Recv.Closed`，`for (m in rx)` 结束。
- **接收端全部消失后**：`send` 让发送任务进入取消展开（不可捕获，执行 `defer`），相当于 Unix 的 SIGPIPE、Kotlin 的 `produce`；`trySend` / `sendTimeout` 返回 `SendResult.Closed`，不取消。长期存在、面向多个接收方的发送方用后两者。发送端已被 `close()` 后再 `send` 是 `E0702` panic（Task331 G11）。
- **显式 `close()`**：两端都有，幂等。`tx.close()` 供仍持有句柄的发送方提前宣布结束；`rx.close()` 供消费方宣布不再接收。
- **`select`**：发送分支同 `send`；接收分支在通道关闭且取空后不再触发；新增 `closed rx => { }` 分支，在关闭且取空时触发；所有分支都不可能再触发时 panic。
- **`isClosed()`**：两端都提供，改为方法，只作提示。
- **`produce`**：`produce<T>(capacity: i64, source: Iterator<T>) -> Receiver<T>`。`source` 与 `T` 须 Sendable，迭代器移入内部任务；迭代器的业务错误类型须为 `Never`；内部任务 panic 时，消费方在读到流末尾处重新抛出，视为已观察（不触发 §6.12）。合流用 `merge(receivers) -> Receiver<T>`。
- **`scope` 的释放顺序**：主体正常结束时，先执行主体的 `defer`，再释放主体中声明的局部绑定，最后等待成员。在 `scope` 内用原始 Channel 写的 worker 池因此不需要 `close()`，也不会死锁。这条规则只影响引用计数的释放时机。
- **模块级常量持有的端点**永不释放、永不自动关闭；退出时的死锁诊断（§6.4）提示"由模块常量持有，需要显式 `close()`"。
- §16.8 的回收时机不变：局部绑定的引用到作用域结束才释放。2026-11-13 补充（[释放时机决策](../../../../xray-docs/analysis/313-decision-release-timing-2026-11-13-cn.md)）：已交出的除外，例如 `go producer(tx)` 是 `tx` 的最后一次使用时，本函数不再持有 `tx`，生产者结束后通道即关闭。在函数级直接使用原始 Channel 时仍可能因本函数持有 `tx` 而等不到结束，由死锁诊断指出（§8.18）。
- 生成器内部挂起（例如等待 I/O）规范已写、尚未实现，随 Task339 M3 落地。

### 6.17 可挂起的 `defer`（C19）

规范 §4.9、§8.3 原先规定 `defer` 体不得挂起或创建任务（`E0392`）。`sync.Mutex` 等待时挂起协程，所以清理代码不能加锁、不能发 Channel、不能 sleep，也不能调用函数类型的参数；标准库已为此两处绕行。本节放开这条限制（§8.19）。

```xray
fn session(conn: ref WsConn, done: Sender<i64>, id: i64) {
    defer {
        ws.close(ref conn)             // 先写关闭帧再关连接：网络写，会挂起
        done.sendTimeout(id, 100)      // 最多等 100 ms：会挂起
    }
    // ...
}
```

- **可以挂起**：是否挂起按每个 `defer` 体推导。含会挂起的 `defer` 的函数是可能挂起的函数；`nosuspend fn` 函数字面量、`CFn` 回调、deinit 与 ISR 中出现这种 `defer` 时照常报错，原因链指向这个 `defer`。不挂起的 `defer` 与今天完全相同。
- **可以创建任务**：`defer` 体里的 `go` 是普通任务。它在词法上位于某个 `scope` 主体内时是该 scope 的成员，否则是独立任务，§6.12 的规则照常适用。要让工作留在清理边界内，写 `scope { go … }` 或等待它。
- **取消屏蔽**：`defer` 体运行期间（含它调用的函数），挂起点与 `Task.checkCancelled()` 不因本任务的取消请求进入展开；`Task.isCancelled()` 照常返回 true。`t.cancel()` 对正在清理的任务只登记请求。清理做完后：
  - 这次退出本来就是取消、panic 或业务错误的展开：继续原来的展开；
  - 这次退出是正常离开（落出、`return`、`break`、`continue`）：照常完成离开，登记的请求在 `defer` 之后的下一个挂起点生效。

  规范 §16.8 已有“清理期间取消被屏蔽”；此前清理不能挂起，这条没有实际作用。
- **由清理体内的操作引起的取消展开**：`defer` 体内（或它调用的函数内）`await` 一个以 `Cancelled` 结束的任务（规范 §10.3），或向接收端已全部消失的通道 `send`（§6.16），仍按普通规则向外传播。展开到达清理边界时：
  - 该 `defer` 体的剩余部分跳过，外层 `defer` 照常执行；
  - 背景是正常离开或业务错误时，任务转为取消展开；
  - 背景是 panic 时 panic 继续，这次取消只作次级诊断；
  - 背景已是取消时继续取消。

  在清理里只想观察结果而不传播时，用 `awaitResult()`、`trySend` 或 `sendTimeout`。
- **不变的规则**：业务错误不得逃出 `defer` 体（`E0387`）；`return` 与跳出清理边界的 `break`、`continue` 非法（`E0395`）；清理期间 panic 的四种背景（规范 §8.2.5）；LIFO 与词法块绑定。
- **`scope`**：顺序不变（§6.16）。主体的 `defer` 先执行，再释放局部绑定，最后等待成员；`defer` 里启动的成员任务在这之后被等待，异常离开时与其它成员一样被取消并等待。
- **生成器除外**：生成器被提前放弃时，它的清理在消费者释放迭代器的地方执行，那里可能不能挂起（对象析构、`nosuspend` 函数）。生成器函数里的 `defer` 维持现行规则：不得挂起、不得创建任务，`E0392` 只保留这一种情形。设计生成器内部挂起时（Task339 M3）再定。
- **限时**：被屏蔽的清理不会被取消打断，清理要给自己限时：用带超时的操作（`sendTimeout`、`recvTimeout`、网络截止时间）或 `Task.timeout(go f(), ms)`。
- **诊断**：任务被请求取消后停在清理里超过阈值（初值同 §6.4 第 4 条的 100 ms，由基准调整）时，sysmon 报出所在 `defer` 的源位置、正在等待的对象与已等待的时长；§6.10 的“谁让程序还活着”清单同样列出这类任务。
- **实现**：
  - 退出阶段是函数自己的可恢复代码。清理里的调用返回 PENDING 时，函数把退出原因（待返回的值、业务错误、panic 或取消）存进帧里再停靠，恢复后接着清理，做完才按退出原因离开。`scope` 退出等待成员用的是同一套记录（规范 §10.7 的“待履行的正常控制转移必须拥有其值并保活主体帧”）。
  - 函数体从未挂起、第一次挂起发生在清理里时，帧在退出阶段才分配（§4 第 1 条照常适用）。
  - 屏蔽是任务上的一个计数，进入 `defer` 体加一、离开减一；取消请求到来时，计数不为零就只登记、不唤醒。
  - 清理体如果按内部函数生成并经引用修改外层局部量，这些局部量按 §4 第 3 条从一开始放进帧；内联进退出路径则没有这个问题，由实施选择。
  - VM 的帧保留退出原因，与 `scope` 退出共用（A6）。
  - 普通函数不再需要 `E0444` 的运行时检查；生成器情形是否保留运行时兜底由实施决定。

### 8.20 阻塞调用补位与长计算补位（C6 修订）

- **问题**：
  - §6.2 原先写“复用 `xworker_blocked.c`、`xworker_sysmon.c`”。前者是 Channel 的等待队列；归档里的队列移交实现已在 2026-06-19 因丢唤醒与孤儿竞态删除，剩下的代码只标记状态。阻塞调用的处理没有可复用的实现。
  - §6.2 原先写“拿不到 worker 就把任务放进全局队列”。阻塞调用返回时，任务接下来要执行的代码在这条线程的 C 栈上，在下一个挂起点之前和线程分不开；这条在无栈模型里做不到。
  - 全部 worker 都被不让出的计算占住时，等待中的任务要等到某个计算结束。Go 靠抢占避免这种情况，原设计只报告。
- **方案**：
  - (a) 不处理，靠窃取；
  - (b) 等队列：队列交给别的线程，返回的线程等到有队列空出来（被删掉的旧实现）；
  - (c) 无队列续跑：队列交给别的线程，返回的线程不带队列跑到下一个调度点（tokio `block_in_place`）；
  - (d) 补位：不移交，启用带自己队列的备用 worker（Java ForkJoinPool 的补偿线程）。
  - 选 (d)，并把同一机制用于长计算。
- **模拟**（单进程离散事件模型，8 核、8 个 worker；纯排队场景与解析解吻合：14.30 µs 对 14.2–16.0 µs）。不做阻塞调用的轻任务的 p99 等待：

  | 负载 | (a) | (b) | (c) | (d) |
  |---|---|---|---|---|
  | 每秒 10 万任务，30% 阻塞 200 µs | 250 ms，积压 | 79 µs | 54 µs | 53 µs |
  | 每秒 5 万任务，1% 阻塞 20 ms | 372 ms，积压 | 4 µs | 4 µs | 1 µs |
  | CPU 约 72%，20% 阻塞 100 µs | 未测 | 144 µs | 103 µs | 101 µs |
  | CPU 约 90%，20% 阻塞 100 µs | 未测 | 45 ms，积压 | 2.2 ms | 1.8 ms |

  - (c) 与 (d) 性能相当，(d) 的线程唤醒更少（CPU 约 72% 时每秒 0.9 万次对 2.0 万次）。选 (d) 的主要理由是没有队列换主人这一步，也就是上次出竞态的那一步。
  - (d) 的休眠条件若用“未被记为长阻塞的 worker 多于 N”，在 CPU 约 90% 的负载下同样积压（p99 15 ms）；所以休眠按“此刻不在调用里”算（§6.2）。
  - 长计算补位：CPU 约 79%、含 200 ms 的不让出计算时，轻任务 p99 等待从 78.5 ms 降到 101 µs，长计算自己的等待中位数多 21 ms。模型按均分 CPU 计算，真实系统的等待会到毫秒级，只取数量级。
- **成本模型**：
  - AOT 运行时：每次外部调用两次存储，不变；每条备用 worker 多一份队列与计时器（按 §6.8 是几 KB 到几十 KB，达到上限时最坏几十 MB）；窃取名单随 worker 数变化；调用返回后运行中的线程短暂多于 N。
  - VM：同一调度器。
  - 编译时间：无影响。
  - 维护：这部分是新写；不需要队列所有权的移交。
  - 长计算补位：超订期间由操作系统分时，长计算按比例变慢。
- **测量**：§10 的阻塞调用补位门、长计算补位门与阻塞调用混合负载基准。
- **放弃条件**：
  - 没有阻塞调用的程序里，§10 任一调度类基准因 worker 集合可变而变慢超过 5%：把备用 worker 放进窃取名单的独立分段，常驻的 N 个 worker 之间的窃取路径保持固定。
  - 长计算补位使“N 个独立计算任务的多核扩展”或不挂起计算的基准下降超过 5%，或在 xray-ports 的真实程序里造成持续超订：提高阈值，或改为只在任务已等待超过阈值时才补位。
- **影响面**：§6.1、§6.2、§6.4、§7；Task328 A5 的“sysmon 只发出警告”；规范 §16.4 的阻塞调用条文与补位相容，待补的仍是线程上限一句（§15）。
- 归档核对、先例、模拟程序与完整结果见[决策记录](../../../../xray-docs/analysis/335-decision-blocking-compensation-2026-11-12-cn.md)。

### 8.21 可能挂起但未挂起的调用路径（C20）

- **问题**：§10 的计算类门只测推导为不挂起、生成普通 C 的函数（fib）。真实的并发程序里，凡是间接碰到锁、Channel 或网络的函数都是可能挂起的函数，它们绝大多数时候并不挂起，这时的速度没有任何门禁。
- **实测**（2026-11-11 与 12 日，Apple M5 Pro，clang 22 与 GCC 16 `-O2`，手写 C 模型；编译期固定变体，4 种代码布局，交替 5 轮取中位数）：
  - 调用约定的开销，相对普通 C：只有调用的递归在 clang 上 1.12–1.31 倍，在 GCC 上 1.59–1.63 倍（GCC 的普通 C 能把递归内联展开，可能挂起的版本不能）；循环里调用存下来的函数值 1.00–1.08 倍。三种约定之间的差别在噪声内，只有 clang 的递归上“上下文里的挂起标志”明显好。
  - 与 Go 1.26.2 相比：三个负载、三种约定的耗时都是 Go 的 0.69–0.86 倍。
  - 代码形状，同步路径相对普通 C：

    | 负载 | 编译器 | 拆分 | 合并 |
    |---|---|---|---|
    | 每次迭代都有一次可能挂起的调用 | clang | 1.04 | 1.03 |
    | 同上 | GCC | 1.02 | 1.97 |
    | 热循环里约每 4096 个元素一次可能挂起的调用 | clang | 0.94 | 2.20 |
    | 同上 | GCC | 1.00 | 1.36 |

  - 体积（clang，两个小函数）：拆分是普通 C 的 3.1–3.3 倍，合并是 2.2–2.4 倍；函数越小比例越高。
- **方案**：
  - (a) 不加门，只靠 fib；
  - (b) 加门，代码形状留给实施；
  - (c) 加门，并规定同步路径上的循环保持单入口。
  - 选 (c)。合并形状的 2 倍退化在 (a) 下任何门都拦不住；(b) 能拦住，但要等到实现之后才发现。
- **门槛的依据**：函数值循环与热循环偶发调用取普通 C 的 1.15 倍，比模型的 0.94–1.08 倍留了余量，给真实代码里模型没有的引用计数等开销。递归一项对 Go 而不对 C：普通 C 在 GCC 下的递归内联是可能挂起的函数先天拿不到的优化，这条路径上要比的是“任何函数都能挂起”的 Go。
- **成本模型**：
  - AOT：循环里含挂起点的可能挂起函数生成两份代码，体积见上。
  - VM：不适用，VM 自己保存帧。
  - 编译时间：这类函数多降级一份。
  - 完成标准：CURRENT_GOAL 的并发性能一条指向本文 §10，这三项因此进入完成标准。
- **测量**：§10 新增的三项基准与生成代码形状门；构建报告里的占比记录（§6.6）。
- **放弃条件**：
  - 某项基准在某个编译器上达不到门槛、两周内定位不到原因：记录差距与原因，由用户决定是否调整门槛；不得用把函数改判为不挂起的办法通过。
  - 拆分使标准库加固定 demo 的原生二进制明显变大：对循环里不含挂起点的函数共用一份代码。“明显”的比例由 S2 的体积数据决定。
- **没测到的**：可能挂起函数的占比（新路径还没有挂起推导的输出）；x86-64 与 MSVC（Windows x64 上超过 8 字节的结构体经内存返回）；真实的生成代码。
- **影响面**：§4 第 9 条、§6.6、§10、§11；Task328 A5 的“一个 resume 函数加一个堆上的帧对象”按 §4 第 9 条细化；规范不受影响。
